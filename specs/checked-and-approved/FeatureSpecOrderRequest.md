# Mealora — Feature Spec: Order Request

**Статус:** checked-and-approved
**Проект:** Mealora
**Тип документа:** Feature Spec
**Зона ответственности:** публичная форма заявки, high-risk отказ, auth gate, отправка заявки и success-состояние
**Дата создания:** 2026-06-20

---

## 1. Назначение документа

Этот документ определяет поведение функции `Order Request / Заявка на заказ` в Mealora v1.

Feature включает:

- страницу `/order-request`;
- выбор параметров недельного плана;
- отображение цены за 5-дневный цикл;
- сбор контактных данных, данных доставки и пищевых пожеланий;
- обязательную проверку high-risk аллергий и строгих медицинских ограничений;
- временное сохранение незавершенной формы перед login/register;
- финальную server-side отправку заявки;
- страницу `/order-request/success`.

Форма создает заявку на ручную проверку Mealora, а не финальный заказ.

Документ имеет статус `checked-and-approved` и является одобренным источником истины для реализации. Результат проверки готовности указан в разделе 19.

## 3. Цель Feature

Feature должна позволить клиенту:

1. выбрать один тип рациона;
2. выбрать один формат питания;
3. указать количество человек от 1 до 5;
4. увидеть цену в `JOD` за стандартный 5-дневный цикл;
5. указать продукты, которые клиент не ест или плохо переносит, уровень остроты и дополнительные пожелания;
6. подтвердить отсутствие high-risk аллергий или строгих медицинских ограничений;
7. заполнить контактные данные и адрес доставки в Зарке;
8. войти или зарегистрироваться перед финальной отправкой;
9. отправить заявку на ручную проверку Mealora;
10. получить понятное подтверждение успешной отправки.

## 4. Scope

### 4.1 Входит в scope

- открытие формы напрямую или после выбора плана;
- изменение плана, формата и количества человек;
- загрузка и отображение активной цены;
- блокировка недоступной комбинации;
- заполнение обязательных и необязательных полей;
- client-side validation;
- server-side validation;
- demo privacy warning;
- high-risk refusal flow;
- login/register gate;
- восстановление незавершенной формы после authentication;
- создание одной записи `order_requests`;
- переход на success page;
- отображение краткого резюме отправленной заявки;
- локализация состояний на `ru` и `en`;
- responsive и accessible behavior.

### 4.2 Не входит в scope

- финальное подтверждение заказа;
- выбор отдельных блюд;
- автоматическая подписка;
- неполная неделя или месячный пакет;
- нестандартные платные адаптации;
- прием заявок с high-risk аллергиями;
- редактирование отправленной заявки клиентом;
- demo payment;
- управление заявкой администратором;
- отправка формы в WhatsApp;
- production consent и прием реальных персональных данных.

## 5. Пользователи и права

### 5.1 Public user

Может:

- открыть `/order-request`;
- заполнить форму;
- менять параметры;
- видеть активную цену;
- временно сохранить данные client-side;
- перейти на login/register.

Не может:

- создать заявку без authentication;
- читать заявки из базы данных;
- передавать доверенный `user_id`, статус или цену.

### 5.2 Authenticated customer

Может:

- восстановить незавершенную форму;
- отправить valid заявку от своего аккаунта;
- после отправки увидеть заявку в личном кабинете.

Не может:

- создать заявку от имени другого пользователя;
- устанавливать `status`, `payment_status` или `admin_notes`;
- редактировать уже отправленную заявку через эту Feature.

## 6. Routes и вход в Feature

Основные routes:

- `/order-request` — форма заявки;
- `/auth/login` — вход перед отправкой;
- `/auth/register` — регистрация перед отправкой;
- `/order-request/success?request_id={id}` — защищенная success page для authenticated владельца заявки;
- `/plans` — возврат к выбору планов;
- `/` — возврат на главную из high-risk refusal;
- `/account/order-requests` — список заявок клиента после отправки.

Вход в форму возможен:

- с `/plans` после выбора плана;
- по прямому URL без заранее выбранного плана;
- после возврата из login/register;
- после browser back, если временные данные еще доступны.

Если план не был выбран до открытия формы, пользователь должен выбрать его внутри формы.

Предварительно выбранный план передается из `/plans` через query parameter:

- route: `/order-request?plan={plan_type}`;
- допустимы только четыре значения plan type из раздела 8.1;
- valid значение автоматически выбирается на первом шаге формы;
- пользователь может изменить предварительно выбранный план;
- отсутствующее, invalid или устаревшее значение игнорируется;
- при отсутствующем или invalid значении пользователь выбирает план вручную;
- query parameter не является доверенным и повторно проверяется client-side и server-side.

## 7. Базовые бизнес-правила

- Одна заявка содержит один тип рациона.
- Одна заявка содержит один формат питания.
- Количество человек: от 1 до 5.
- Стандартный цикл: 5 дней, воскресенье–четверг.
- Валюта: `JOD`.
- География доставки: Зарка, Иордания.
- Preferred start date не является финально подтвержденной датой.
- Mealora вручную подтверждает доступность, старт и детали.
- Заявка после успешной отправки получает `status = submitted`.
- Заявка после успешной отправки получает `payment_status = not_required`.
- Только `confirmed` означает финальный заказ.
- WhatsApp используется только для последующих ручных уточнений, а не как техническое место отправки формы.
- Заявка, отправленная после субботы 12:00 по `Asia/Amman`, не гарантирует старт в ближайшее воскресенье.

## 8. Параметры плана и цена

### 8.1 Тип рациона

Допустимые технические значения и display labels:

| `plan_type` | Display label |
|---|---|
| `balanced` | `Balanced Plan` |
| `calorie_control` | `Calorie-Control Plan` |
| `sport` | `Sport Plan` |
| `light_gentle` | `Light / Gentle Plan` |

### 8.2 Формат питания

Допустимые технические значения и display labels:

| `meal_format` | Display label |
|---|---|
| `one_daily_meal` | `One daily meal` |
| `lunch_and_dinner` | `Lunch and Dinner` |

Технические значения одинаково используются в query parameter, database, API payloads, `order_requests`, `price_options` и client/server validation. Display labels локализуются для пользователя.

### 8.3 Количество человек

- допустимый диапазон: `1–5`;
- основной публичный термин: `количество человек`;
- термин `порции` не используется как название этого параметра.

### 8.4 Расчет цены

Цена определяется комбинацией:

- `plan_type`;
- `meal_format`;
- `people_count`;
- `cycle_days = 5`;
- `currency = JOD`;
- `active = true`.

Публичная форма может показывать цену, полученную из active `price_options`, но client-side значение не является источником истины.

Перед созданием заявки server обязан повторно найти active price и сохранить snapshot в `order_requests.cycle_price`.

Если active price не найдена:

- submit блокируется;
- заявка не создается;
- пользователь видит спокойное локализованное сообщение о временной недоступности комбинации.

При изменении плана, формата или количества человек цена должна быть рассчитана заново.

Поведение цены:

- во время загрузки показывается спокойный loading state;
- пока цена загружается, переход к финальной отправке блокируется;
- ранее выбранные параметры формы сохраняются;
- при временной сетевой ошибке показывается локализованное сообщение и действие повторной загрузки;
- повторная загрузка использует текущие выбранные plan, format и people count;
- при сетевой ошибке пользователь может изменить параметры и запустить новый расчет;
- при inactive или отсутствующей active цене комбинация считается недоступной;
- недоступная комбинация блокирует отправку и предлагает изменить параметры;
- server-side price lookup остается финальным источником истины.

Если цена изменилась между отображением итогового шага и финальной отправкой:

- server не создает заявку с устаревшей ценой;
- server возвращает error code `price_changed`, ранее показанную цену и новую active цену;
- пользователь остается на четвертом шаге;
- введенные данные и выбранные параметры сохраняются;
- итог заявки обновляется новой ценой;
- UI явно показывает старую и новую сумму в `JOD`;
- пользователь должен проверить новую сумму и повторно нажать `Отправить заявку`;
- новая цена не считается подтвержденной автоматически;
- после подтверждения новой цены создается новый `idempotency_key`;
- повторная отправка снова проходит server-side price lookup;
- если комбинация стала inactive или цена исчезла, используется `price_unavailable`, отправка блокируется и пользователь должен изменить параметры.

## 9. Поля формы

### 9.1 Структура формы

Форма является пошаговой и состоит из четырех этапов:

1. `План и цена`:
   - тип рациона;
   - формат питания;
   - количество человек;
   - цена за 5-дневный цикл.
2. `Предпочтения и ограничения`:
   - продукты, которые клиент не ест или плохо переносит;
   - уровень остроты;
   - дополнительные пожелания;
   - обязательный high-risk вопрос.
3. `Контакты и доставка`:
   - имя;
   - телефон / WhatsApp;
   - зона доставки из утвержденного списка районов Зарки;
   - точный адрес;
   - предпочтительный стартовый недельный цикл.
4. `Проверка и отправка`:
   - итоговое резюме заявки;
   - возможность вернуться к предыдущим шагам и исправить данные;
   - login/register gate перед финальной отправкой;
   - основной CTA `Отправить заявку`.

Состав резюме четвертого шага:

- display label выбранного плана;
- display label формата питания;
- количество человек;
- актуальная цена в `JOD`;
- полный текст продуктов, которые клиент не ест или плохо переносит;
- выбранный уровень остроты или `Не указано`;
- полный текст дополнительных пожеланий или `Не указаны`;
- high-risk ответ;
- имя клиента;
- полный номер WhatsApp;
- зона доставки;
- полный точный адрес;
- preferred start date или `Не указана`;
- возле каждого смыслового блока доступно действие `Изменить`, возвращающее на соответствующий шаг без потери данных.

На каждом шаге показывается понятный индикатор прогресса с текущим номером и общим количеством шагов.

Пользователь может переходить назад к уже заполненным шагам без потери введенных данных. Изменение плана, формата или количества человек должно повторно запустить расчет цены и обновить итог заявки.

Правила перехода между шагами:

- кнопка `Продолжить` проверяет обязательные поля и допустимые значения только текущего шага;
- переход вперед блокируется, пока текущий шаг не пройдет client-side validation;
- ошибка показывается рядом с соответствующим полем и в спокойном тоне;
- при невалидном поле focus переводится к первому невалидному полю текущего шага;
- переход назад разрешен без validation и без потери введенных данных;
- необязательные поля можно пропускать;
- шаг 1 требует valid plan, meal format, people count и загруженную active цену;
- шаг 2 требует допустимый high-risk ответ; значение `Нет`, выбранное по умолчанию, является valid подтверждением;
- при ответе `Да` переход вперед и отправка блокируются согласно high-risk flow;
- шаг 3 требует valid имя, мобильный номер Иордании, зону доставки и точный адрес;
- шаг 4 перед auth gate и финальным submit повторно проверяет всю форму;
- после login/register восстановленная форма повторно проходит полную client-side validation;
- server-side validation всех critical данных остается обязательной независимо от успешной проверки шагов.

### 9.2 Обязательные данные

| Данные | Техническое поле | Правило |
|---|---|---|
| Тип рациона | `plan_type` | Одно из четырех допустимых значений |
| Формат питания | `meal_format` | Одно из двух допустимых значений |
| Количество человек | `people_count` | Целое число от 1 до 5 |
| Цена цикла | `cycle_price` | Server-side snapshot active цены в `JOD` |
| Имя клиента | `customer_name` | Непустое значение |
| Телефон / WhatsApp | `customer_whatsapp` | Valid мобильный номер Иордании |
| Зона доставки | `delivery_city_or_zone` | Значение из утвержденного списка районов Зарки |
| Адрес доставки | `delivery_address` | Непустое значение |
| High-risk ответ | `high_risk_answer` | `no` для создания заявки |
| High-risk подтверждение | `high_risk_confirmed_no` | `true` для создания заявки |

Зона доставки и точный адрес являются разными полями:

- зона выбирается из списка;
- точный адрес вводится отдельной строкой;
- свободный ввод зоны доставки не используется;
- значение зоны повторно проверяется server-side по тому же утвержденному allowlist;
- если зона отсутствует в списке, отправка блокируется и заявка не создается.

Утвержденный allowlist зон доставки v1:

| Техническое значение | Русское название | English name |
|---|---|---|
| `city_center` | Центр города | City Center |
| `al_thawra` | Аль-Таура Аль-Арабия | Al-Thawra Al-Arabiya |
| `awajan` | Аваджан | Awajan |
| `zawahreh` | Завахре | Zawahreh |
| `new_zarqa` | Новая Зарка | New Zarqa |

Другие зоны, включая Russeifa и Hashemite District, не входят в delivery scope v1 и не принимаются автоматически через публичную форму.

Правила телефона / WhatsApp:

- принимаются только мобильные номера Иордании;
- пользователь может ввести локальный формат `07XXXXXXXX` — 10 цифр;
- пользователь может ввести международный формат `+9627XXXXXXXX`;
- пробелы, дефисы и круглые скобки могут быть удалены при normalization;
- перед сохранением локальный формат преобразуется в `+9627XXXXXXXX`;
- `customer_whatsapp` хранится в нормализованном международном формате;
- номера с другим country code отклоняются;
- стационарные номера и иорданские номера, не соответствующие мобильному формату, отклоняются;
- номер используется Mealora для WhatsApp-связи и ручных уточнений по заявке.

### 9.3 Необязательные данные

Форма использует следующие необязательные UI-поля:

- `Продукты, которые вы не едите или плохо переносите` — одно объединенное текстовое поле для нежелательных продуктов, нелюбимых продуктов и легких непереносимостей;
- `Уровень остроты` — отдельный выбор;
- `Дополнительные пожелания` — отдельное текстовое поле;
- `Предпочтительный стартовый недельный цикл` — необязательный выбор только ближайшего будущего воскресенья.

Объединенное поле не предназначено для тяжелых аллергий или строгих медицинских ограничений. Такие ограничения обрабатываются только через обязательный high-risk вопрос.

Правила сохранения:

- значение объединенного поля сохраняется в `excluded_foods`;
- `spice_level` хранит выбранный уровень остроты;
- `additional_notes` хранит дополнительные пожелания;
- `food_preferences` и `mild_intolerances` не заполняются публичной формой v1 и остаются `null`;
- `preferred_start_date` хранит дату ближайшего будущего воскресенья в календарном формате даты.

Правила preferred start date:

- поле является необязательным;
- пользователю доступно только ближайшее будущее воскресенье по `Asia/Amman`;
- текущая календарная дата никогда не считается будущей датой: если форма открыта в воскресенье, доступно воскресенье следующей недели;
- прошедшие даты, текущее воскресенье, остальные дни недели и более поздние воскресенья недоступны;
- доступная дата пересчитывается по календарю `Asia/Amman` при загрузке формы и перед server-side отправкой;
- выбранная дата является пожеланием, а не подтвержденной датой старта;
- Mealora подтверждает фактическую дату вручную после проверки заявки;
- если ближайшее воскресенье выбрано после субботы 12:00 по `Asia/Amman`, форма не блокирует отправку, но показывает предупреждение, что старт в ближайшем цикле не гарантирован;
- success page повторяет, что дата будет подтверждена Mealora.

### 9.4 Ограничения полей

Frontend и server используют одинаковые ограничения после normalization.

#### Имя клиента

- обязательное поле;
- длина: от 2 до 80 символов;
- разрешены Unicode-буквы любых языков, пробел, дефис `-`, прямой апостроф `'` и типографский апостроф `’`;
- цифры, emoji, URL, email-адреса и другие специальные символы не разрешены;
- имя не может состоять только из пробелов, дефисов или апострофов.

#### Телефон / WhatsApp

- обязательное поле;
- применяется формат и normalization из раздела 9.2;
- после normalization допустим только формат `+9627XXXXXXXX`.

#### Зона доставки

- обязательный выбор одного значения из утвержденного allowlist;
- свободный пользовательский ввод не принимается.

#### Точный адрес

- обязательное поле;
- длина: от 5 до 250 символов;
- разрешены Unicode-буквы, цифры, пробелы и обычные адресные знаки: `-`, `/`, `.`, `,`, `'`, `’`, `(`, `)`, `#`;
- emoji, HTML-теги и управляющие символы не разрешены.

#### Продукты, которые вы не едите или плохо переносите

- необязательное поле;
- максимальная длина: 500 символов;
- разрешен обычный Unicode-текст, цифры, пробелы и базовая пунктуация;
- HTML-теги и управляющие символы не разрешены.

#### Уровень остроты

Необязательное поле со следующими сохраняемыми значениями:

- `none` — `Без остроты` / `Not spicy`;
- `mild` — `Легкая острота` / `Mild`;
- `medium` — `Средняя острота` / `Medium`;
- `hot` — `Остро` / `Hot`.

UI может показывать вариант `Не указывать` / `Not specified`, но он не является техническим значением и сохраняется как `null`.

#### Дополнительные пожелания

- необязательное поле;
- максимальная длина: 500 символов;
- разрешен обычный Unicode-текст, цифры, пробелы и базовая пунктуация;
- HTML-теги и управляющие символы не разрешены.

#### Preferred start date

- применяется правило выбора только ближайшего будущего воскресенья из раздела 9.3;
- дата сохраняется без времени в формате `YYYY-MM-DD`;
- интерпретация календарной даты выполняется по `Asia/Amman`.

#### Общая normalization

- в однострочных полях удаляются пробелы в начале и конце;
- несколько последовательных пробелов внутри однострочного поля заменяются одним;
- в многострочных полях удаляются пробелы в начале и конце всего значения;
- переносы строк нормализуются в `LF`;
- три и более пустые строки подряд сокращаются до двух;
- пустая строка в необязательном поле сохраняется как `null`;
- HTML не выполняется и не интерпретируется как markup;
- frontend может показывать ошибку раньше, но server повторяет все проверки;
- длина измеряется после normalization в Unicode code points.

## 11. High-risk allergy flow

Обязательный вопрос:

> Есть ли у вас тяжелые аллергии или строгие медицинские ограничения?

Варианты:

- `Нет`;
- `Да`.

По одобренному Business Spec значение по умолчанию — `Нет`.

### 11.1 Ответ `Нет`

- flow продолжается;
- в заявке сохраняется `high_risk_answer = no`;
- в заявке сохраняется `high_risk_confirmed_no = true`.

### 11.2 Ответ `Да`

- открывается High-Risk Allergy Refusal Modal;
- заявка не создается;
- данные не отправляются команде Mealora как обычная заявка;
- модальное окно спокойно объясняет риск перекрестного контакта и отсутствие отдельного безопасного процесса приготовления;
- пользователь может закрыть modal и вернуться к форме, чтобы исправить ошибочно выбранный ответ;
- после закрытия modal ответ остается `Да`, пока пользователь явно не изменит его на `Нет`;
- пока выбран ответ `Да`, переход к финальной отправке и создание заявки заблокированы;
- пользователь может перейти на главную через отдельный CTA `Вернуться на главную страницу Mealora`.

Server обязан отклонить payload с:

- `high_risk_answer = yes`;
- `high_risk_confirmed_no != true`.

Закрытие modal не означает согласие Mealora принять high-risk заявку и не изменяет ответ автоматически.

## 12. Auth gate и временное сохранение

Пользователь может начать форму без аккаунта, но не может отправить ее без authentication.

Если unauthenticated user нажимает финальный submit:

1. приложение выполняет client-side validation;
2. valid данные временно сохраняются client-side;
3. пользователь направляется на login или register;
4. после успешной authentication пользователь возвращается к заявке;
5. временные данные восстанавливаются;
6. пользователь подтверждает финальную отправку;
7. все данные повторно проходят client-side и server-side validation.

Технические правила:

- временное хранилище — `sessionStorage` текущей вкладки;
- draft записывается после каждого изменения поля и перехода между шагами с debounce `300ms`;
- draft хранит нормализуемые данные формы, выбранную локаль и номер текущего шага;
- transient UI states не сохраняются: validation errors, loading, refusal modal, submitting и submit error;
- временные данные не являются доверенными;
- `cycle_price`, `user_id`, `status`, `payment_status` и admin fields не принимаются из временного хранилища как источник истины;
- после успешного создания заявки временные данные очищаются;
- draft существует только в рамках browser session текущей вкладки и удаляется при закрытии вкладки;
- draft очищается при logout;
- draft очищается при смене authenticated пользователя;
- draft, созданный до authentication, связывается с user id после успешного входа и не восстанавливается для другого пользователя;
- разные вкладки имеют независимые drafts и не синхронизируют данные между собой;
- после refresh форма восстанавливает данные, локаль и текущий шаг;
- после восстановления client выполняет validation уже пройденных шагов;
- если предыдущий шаг стал invalid, пользователь переводится на первый invalid шаг;
- сохраненная цена может использоваться только как ранее показанная сумма, но не как актуальная active цена;
- после refresh active цена обязательно загружается заново с server;
- до завершения повторной загрузки цены переход вперед и submit блокируются;
- если цена не изменилась, пользователь остается на восстановленном valid шаге;
- если цена изменилась, применяется `price_changed` с явным повторным подтверждением;
- если цена стала недоступной, пользователь переводится на шаг 1 для изменения параметров;
- после восстановления форма повторно проходит client-side validation;
- перед созданием заявки все critical данные повторно проходят server-side validation;
- поврежденные, устаревшие или invalid данные не отправляются и должны быть исправлены пользователем;
- изменение локали и переход между login/register в той же вкладке не должны очищать valid draft;
- в demo-версии во временное хранилище разрешено помещать только вымышленные тестовые данные согласно demo warning.

На auth gate пользователь может выбрать login или register. После успешного действия оба flow возвращают пользователя к сохраненной форме в той же вкладке.

## 13. Финальная отправка

Заявка создается только через controlled server endpoint или server action.

Последовательность:

1. Customer подтверждает submit.
2. Client создает уникальный `idempotency_key` для этой попытки создания заявки.
3. UI блокирует повторное нажатие на время запроса и показывает состояние отправки.
4. Server проверяет authenticated session.
5. `user_id` берется только из session.
6. Server проверяет обязательные поля и enum-значения.
7. Server проверяет `people_count`.
8. Server отклоняет high-risk заявку.
9. Server проверяет поддерживаемую delivery zone.
10. Server находит active price.
11. Server проверяет `idempotency_key` для authenticated customer.
12. Server сохраняет snapshot цены.
13. Server создает `order_requests` со значениями:
    - `user_id` из session;
    - `status = submitted`;
    - `payment_status = not_required`;
    - validated form data;
    - `cycle_price` из server-side price lookup;
    - уникальная связь с `idempotency_key`.
14. Client очищает временные данные.
15. Client переходит на `/order-request/success?request_id={id}`, используя ID созданной или ранее созданной idempotent-заявки.

Заявка не создается, если хотя бы одна critical validation не пройдена.

Правила защиты от дубликатов:

- один `idempotency_key` соответствует одной логической отправке формы одним customer;
- повторный запрос с тем же key не создает вторую заявку;
- если первая отправка уже создала заявку, повторный запрос возвращает результат существующей заявки;
- при network timeout client повторяет запрос с тем же key, пока пользователь не изменил форму и не начал новую логическую отправку;
- key должен проверяться вместе с authenticated `user_id`, чтобы значение другого пользователя не могло вернуть чужую заявку;
- создание заявки и фиксация key должны выполняться атомарно;
- server должен обеспечить уникальность пары `user_id + idempotency_key`;
- после явного изменения формы и новой попытки пользователь получает новый key;
- disabled кнопка является UI-защитой, но server-side idempotency остается обязательной.

Правила timeout и retry:

- client не выполняет автоматический retry после timeout;
- после timeout показывается сообщение `Не удалось подтвердить результат отправки. Проверьте соединение и попробуйте еще раз.` / `We could not confirm the submission result. Check your connection and try again.`;
- пользователь получает CTA `Проверить и повторить` / `Check and retry`;
- перед первым запросом `idempotency_key` сохраняется в отдельной pending-записи в `sessionStorage` текущей вкладки;
- pending-запись содержит `idempotency_key`, fingerprint normalized submission payload и количество попыток;
- pending-запись не заменяет основной draft формы;
- при ручном retry неизмененной формы используется тот же `idempotency_key`;
- допускается максимум 3 попытки с одним key, включая первую отправку как attempt 1;
- во время каждой попытки CTA блокируется и показывает submitting state;
- если server уже создал заявку, повтор возвращает существующий `request_id`;
- после третьей неудачной попытки retry CTA скрывается, а пользователь получает переход в `/account/order-requests`;
- изменение любого поля, влияющего на submission payload, после timeout инвалидирует pending-запись; следующая отправка получает новый key и attempt count начинается заново;
- pending-запись очищается после успешного результата, logout, смены пользователя или закрытия вкладки;
- refresh при наличии pending-записи не отправляет запрос автоматически, а восстанавливает timeout-состояние и CTA `Проверить и повторить`;
- fingerprint используется только для сравнения неизменности payload и не является источником истины для server validation.

## 14. Success page

После успешного создания заявки пользователь переходит на `/order-request/success?request_id={id}`.

Success page получает `request_id` созданной заявки через query parameter:

- route: `/order-request/success?request_id={id}`;
- page проверяет authenticated session server-side;
- page server-side загружает заявку только при совпадении `order_requests.user_id` с authenticated user id;
- client не может использовать ID для чтения заявки другого customer;
- резюме строится из сохраненной server-side записи, а не из client draft;
- refresh страницы повторно загружает ту же заявку и не создает новую;
- если `request_id` отсутствует, invalid, не найден или не принадлежит текущему customer, пользователь перенаправляется на `/account/order-requests`;
- внутренние `admin_notes` и другие закрытые данные не включаются в ответ success page;
- expired или отсутствующая session перенаправляет пользователя на `/auth/login`; после успешного входа пользователь возвращается на исходный success route с сохраненным `request_id`.

Страница должна:

- подтвердить отправку заявки;
- не называть заявку финальным заказом;
- показать краткое резюме;
- объяснить ручную проверку Mealora;
- сообщить, что статус доступен в личном кабинете;
- предупредить о возможном уточнении через WhatsApp;
- объяснить, что старт и детали подтверждаются вручную;
- напомнить о дедлайне: суббота 12:00 по `Asia/Amman`;
- дать переход в `/account/order-requests`;
- дать переход на `/` или `/plans`.

Состав резюме success page:

- короткое отображение ID заявки;
- статус `submitted` с локализованным объяснением;
- display label плана;
- display label формата питания;
- количество человек;
- сохраненная `cycle_price` в `JOD`;
- preferred start date или `Не указана`;
- имя клиента;
- маскированный WhatsApp в формате вида `+962 7X *** **34`;
- зона доставки;
- маскированный адрес: первые 20 Unicode code points и `…`, если адрес длиннее;
- признак наличия пищевых пожеланий без полного текста;
- high-risk подтверждение `Тяжелые аллергии не указаны` / `No severe allergies indicated`.

Success page не показывает:

- полный WhatsApp;
- полный адрес;
- полный текст пищевых ограничений или дополнительных пожеланий;
- `user_id`;
- `idempotency_key`;
- `admin_notes`;
- внутренние технические поля и payload fingerprint.

Страница не должна:

- показываться как подтверждение оплаты;
- обещать старт в ближайшее воскресенье;
- создавать впечатление, что заказ уже `confirmed`.

Прямое открытие route допустимо только с valid `request_id` собственной заявки authenticated customer.

## 15. Validation и ошибки

### 15.1 Client-side validation

Client-side validation используется для быстрого feedback, но не заменяет server-side validation.

Submit блокируется, если:

- отсутствует обязательное поле;
- выбран invalid plan или format;
- `people_count` вне диапазона;
- цена отсутствует;
- high-risk ответ `Да`;
- high-risk подтверждение `Нет` отсутствует;
- delivery zone явно не поддерживается.

### 15.2 Server-side validation

Server отклоняет запрос, если:

- session отсутствует или истекла;
- обязательные поля отсутствуют;
- enum или диапазон invalid;
- high-risk ответ не разрешает создание;
- active price не найдена;
- client price не совпадает с server-side расчетом;
- delivery zone не поддерживается;
- payload содержит попытку установить защищенные поля.

### 15.3 Ошибки отправки

При server или database error:

- заявка не считается отправленной;
- success page не открывается;
- submit снова становится доступным;
- введенные данные не должны без необходимости теряться;
- показывается спокойный локализованный fallback без внутренних технических деталей.

Примеры тона:

- `Укажите номер телефона.`;
- `Выберите вариант.`;
- `Проверьте введенные данные.`;
- `Не удалось отправить заявку. Попробуйте еще раз.`;
- `Эта комбинация сейчас недоступна. Выберите другой вариант.`

Эти validation messages являются утвержденным контрактом текущей Feature. Будущий `FeatureSpecContent.md` может централизовать тексты только без изменения смысла и error-code mapping либо после отдельного одобрения владельца проекта.

## 17. Локализация, UI и доступность

- Клиентский интерфейс поддерживает `ru` и `en`.
- `ru` используется по умолчанию.
- Изменение языка не сбрасывает форму, выбранный план или цену.
- Validation, errors, loading, refusal и success показываются на активной локали.
- В пределах локали нельзя без необходимости смешивать русский и английский.
- Официальные названия планов могут оставаться на английском рядом с понятным объяснением.
- Форма не должна выглядеть как медицинская анкета.
- Focus states должны быть видимыми.
- Ошибка не передается только цветом.
- Touch target на mobile: минимум `44px`.
- Контраст соответствует WCAG AA.
- Кнопки и поля выдерживают длину русских и английских текстов.
- CTA используют спокойный тон: `Продолжить`, `Отправить заявку`, а не агрессивный ecommerce-copy.

Визуальная реализация должна сохранять утвержденные четыре шага, понятный progress indicator и возможность возврата без потери данных.

---

## 18. Безопасность и данные

- Public user не читает `order_requests`.
- Customer читает только собственные заявки.
- `user_id` нельзя принимать из client payload.
- `status`, `payment_status` и `admin_notes` нельзя устанавливать через публичную форму.
- Service role key не попадает в browser.
- Server-side ownership и role checks обязательны.
- RLS включена для связанных application tables.
- Логи не должны без необходимости содержать полные контактные данные, адрес или пищевые ограничения.
- Неуспешная или high-risk отправка не создает database record.
- Demo-версия не принимает реальные персональные, адресные или чувствительные данные.

## 20. Закрытые решения

### 20.1 Поля пищевых предпочтений

Владелец проекта утвердил:

- одно объединенное поле `Продукты, которые вы не едите или плохо переносите`;
- отдельное поле `Уровень остроты`;
- отдельное поле `Дополнительные пожелания`;
- объединенное поле не используется для high-risk аллергий или строгих медицинских ограничений;
- high-risk ограничения обрабатываются отдельным обязательным вопросом.

### 20.2 Структура формы

Владелец проекта утвердил:

- пошаговую форму из четырех этапов;
- этап 1: план и цена;
- этап 2: предпочтения и ограничения;
- этап 3: контакты и доставка;
- этап 4: проверка и отправка;
- понятный индикатор прогресса;
- возврат к предыдущим шагам без потери данных.

### 20.3 Зоны доставки

Владелец проекта утвердил:

- зона доставки выбирается только из утвержденного списка районов Зарки;
- allowlist v1: `city_center`, `al_thawra`, `awajan`, `zawahreh`, `new_zarqa`;
- используется select, а не свободный ввод зоны;
- точный адрес вводится в отдельном обязательном поле;
- frontend и server используют один логический allowlist поддерживаемых зон;
- неподдерживаемая зона блокирует отправку;
- заявка с неподдерживаемой зоной не создается;
- пользователю показывается спокойное локализованное сообщение о недоступности доставки.

### 20.4 Телефон / WhatsApp

Владелец проекта утвердил:

- v1 принимает только мобильные номера Иордании;
- локальный формат ввода: `07XXXXXXXX`;
- международный формат ввода: `+9627XXXXXXXX`;
- номер нормализуется и хранится как `+9627XXXXXXXX`;
- номера других стран не принимаются;
- стационарные и invalid мобильные номера не принимаются;
- номер используется для WhatsApp-связи и ручных уточнений по заявке.

### 20.5 Предпочтительная дата старта

Владелец проекта утвердил:

- поле является необязательным;
- выбирается только ближайшее будущее воскресенье;
- если форма открыта в воскресенье, ближайшей будущей датой считается воскресенье следующей недели;
- более поздние воскресенья выбрать нельзя;
- дата интерпретируется по `Asia/Amman`;
- выбранная дата является пожеланием клиента;
- Mealora подтверждает фактическую дату старта вручную;
- отправка после субботы 12:00 не блокируется;
- для ближайшего воскресенья после дедлайна показывается предупреждение, что старт не гарантирован.

### 20.6 High-risk refusal modal

Владелец проекта утвердил:

- при ответе `Да` modal показывает вежливый отказ;
- modal можно закрыть и вернуться в форму для исправления ошибочного ответа;
- закрытие modal не меняет ответ автоматически;
- пока выбран ответ `Да`, заявку отправить нельзя;
- для продолжения пользователь должен явно изменить ответ на `Нет`;
- отдельный CTA позволяет вернуться на главную страницу Mealora;
- high-risk заявка ни при каких действиях modal не создается.

### 20.7 Временное сохранение формы

Владелец проекта утвердил:

- незавершенная форма хранится в `sessionStorage` текущей вкладки;
- draft сохраняется при переходе на login/register и возвращении к форме;
- разные вкладки используют независимые drafts;
- draft не синхронизируется между вкладками;
- draft очищается после успешной отправки, logout, смены пользователя или закрытия вкладки;
- draft одного пользователя не восстанавливается для другого пользователя;
- изменение языка не сбрасывает valid draft;
- восстановленные данные повторно проходят client-side и server-side validation;
- временные данные не являются источником истины для цены, пользователя или управляемых системой статусов;
- в demo-версии разрешены только вымышленные тестовые данные.

### 20.8 Защита от дублирования

Владелец проекта утвердил:

- после первого submit кнопка блокируется и показывает состояние отправки;
- каждая логическая отправка получает уникальный `idempotency_key`;
- повторный запрос с тем же key не создает вторую заявку;
- после timeout повтор используется с тем же key;
- если заявка уже создана, server возвращает существующий результат;
- уникальность проверяется по паре `user_id + idempotency_key`;
- фиксация key и создание заявки выполняются атомарно;
- новая логическая отправка после изменения формы получает новый key;
- server-side защита обязательна независимо от disabled состояния кнопки.

### 20.9 Данные success page

Владелец проекта утвердил:

- после отправки используется `/order-request/success?request_id={id}`;
- success page загружает заявку server-side;
- заявка показывается только authenticated владельцу;
- резюме строится из сохраненной записи;
- refresh не создает новую заявку и повторно показывает ту же запись;
- отсутствующий, invalid, несуществующий или чужой ID приводит к редиректу на `/account/order-requests`;
- закрытые административные данные не возвращаются на success page.

### 20.10 Ограничения и validation полей

Владелец проекта утвердил:

- единые frontend и server-side ограничения из раздела 9.4;
- имя длиной от 2 до 80 символов с Unicode-буквами, пробелами, дефисами и апострофами;
- точный адрес длиной от 5 до 250 символов;
- текстовые пожелания длиной не более 500 символов;
- фиксированные значения `spice_level`;
- normalization пробелов, пустых значений и переносов строк;
- запрет управляющих символов и интерпретации HTML;
- одинаковые error codes и утвержденные сообщения на русском и английском языках.

### 20.11 Передача выбранного плана

Владелец проекта утвердил:

- выбранный plan передается через `/order-request?plan={plan_type}`;
- принимаются только четыре допустимых plan type;
- valid значение предварительно выбирается на первом шаге;
- пользователь может изменить выбор;
- отсутствующее, invalid или устаревшее значение игнорируется;
- query parameter повторно валидируется и не считается доверенным.

### 20.12 Загрузка и ошибка цены

Владелец проекта утвердил:

- во время загрузки показывается спокойный loading state;
- финальная отправка блокируется до получения valid цены;
- выбранные параметры не теряются;
- при сетевой ошибке показывается локализованная ошибка и повторная загрузка;
- пользователь может изменить параметры после ошибки;
- inactive или отсутствующая active цена блокирует комбинацию;
- server-side price lookup является финальным источником истины.

### 20.13 Технические значения plan и meal format

Владелец проекта утвердил:

- `Balanced Plan` → `balanced`;
- `Calorie-Control Plan` → `calorie_control`;
- `Sport Plan` → `sport`;
- `Light / Gentle Plan` → `light_gentle`;
- `One daily meal` → `one_daily_meal`;
- `Lunch and Dinner` → `lunch_and_dinner`;
- значения одинаково используются в URL, database, API и validation;
- пользователь видит локализованные display labels, а не технические значения.

### 20.14 Валидация шагов

Владелец проекта утвердил:

- переход вперед только после successful validation текущего шага;
- показ ошибки рядом с полем и focus на первом невалидном поле;
- переход назад без validation и потери данных;
- возможность пропустить необязательные поля;
- проверку plan, format, people count и active цены на шаге 1;
- проверку high-risk ответа на шаге 2;
- значение `Нет` по умолчанию является valid подтверждением;
- проверку имени, телефона, зоны и адреса на шаге 3;
- полную повторную validation на шаге 4 и после возврата из authentication;
- обязательную server-side validation перед созданием заявки.

### 20.15 Изменение цены перед отправкой

Владелец проекта утвердил:

- server повторно определяет active цену перед созданием заявки;
- при изменении цены заявка не создается;
- server возвращает `price_changed`, старую и новую цену;
- пользователь остается на четвертом шаге без потери данных;
- итог обновляется и показывает обе суммы в `JOD`;
- новая цена требует явного повторного подтверждения;
- повторная отправка использует новый `idempotency_key`;
- если цена стала недоступной, используется `price_unavailable` и отправка блокируется.

### 20.16 Сохранение и восстановление после refresh

Владелец проекта утвердил:

- autosave draft после изменений и переходов между шагами с debounce `300ms`;
- сохранение полей, локали и текущего шага в `sessionStorage` текущей вкладки;
- transient UI states не сохраняются;
- после refresh восстанавливаются данные, локаль и шаг;
- invalid предыдущие шаги возвращают пользователя к первому invalid шагу;
- active цена всегда загружается повторно с server;
- до загрузки цены переход вперед и submit заблокированы;
- неизменившаяся цена сохраняет восстановленный шаг;
- изменившаяся цена использует `price_changed`;
- недоступная цена возвращает пользователя на шаг 1;
- существующие правила очистки draft остаются обязательными.

### 20.17 Timeout и ручный retry

Владелец проекта утвердил:

- отсутствие автоматического retry;
- спокойное сообщение `submit_timeout`;
- CTA `Проверить и повторить`;
- отдельную pending-запись с key, payload fingerprint и attempt count в `sessionStorage`;
- использование того же key для неизмененной формы;
- максимум 3 попытки с одним key, включая первую отправку;
- возврат существующего `request_id`, если заявка уже создана;
- после трех неудач переход к списку заявок вместо дальнейшего retry;
- изменение payload создает новый key и новый attempt count;
- очистку pending-записи после успеха, logout, смены пользователя или закрытия вкладки;
- после refresh восстановление retry-состояния без автоматической отправки.

### 20.18 Состав резюме и маскирование

Владелец проекта утвердил:

- полное резюме всех пользовательских данных на четвертом шаге до отправки;
- действия `Изменить` для возврата к соответствующему шагу;
- сокращенное резюме на success page;
- маскирование WhatsApp и точного адреса на success page;
- отсутствие полного текста пищевых ограничений и пожеланий на success page;
- отображение только факта наличия таких пожеланий;
- запрет показа `user_id`, `idempotency_key`, `admin_notes`, fingerprint и внутренних технических полей;
- использование server-side сохраненной записи как источника success summary.

### 20.19 Максимальный срок preferred start date

Владелец проекта утвердил:

- доступно только ближайшее будущее воскресенье по `Asia/Amman`;
- текущая дата не считается будущей;
- если форма открыта в воскресенье, доступно воскресенье следующей недели;
- прошедшие даты, остальные дни недели и более поздние воскресенья недоступны;
- после субботы 12:00 ближайшее воскресенье остается доступным, но старт в этом цикле не гарантируется;
- Mealora подтверждает фактическую дату старта вручную.

## 21. Критерии приемки после закрытия открытых решений

Feature может считаться готовой к реализации, если:

- форма явно создает заявку, а не финальный заказ;
- все обязательные поля и ограничения утверждены;
- plan, format и people count проходят client-side и server-side validation;
- цена показывается в `JOD` и повторно определяется server-side;
- inactive или отсутствующая цена блокирует создание заявки;
- high-risk ответ `Да` не создает заявку;
- high-risk ответ `Нет` сохраняется как подтверждение;
- preferred start date, если указана, равна ближайшему будущему воскресенью по `Asia/Amman`;
- demo warning показывается до контактных и чувствительных полей;
- unauthenticated user не может создать заявку;
- данные формы восстанавливаются после login/register по утвержденным правилам;
- `user_id` берется из session;
- valid submit создает одну запись со статусами `submitted` и `not_required`;
- customer и admin видят созданную заявку в соответствующих защищенных интерфейсах;
- submit error не открывает success page и не уничтожает valid input;
- success page не обещает финальный заказ;
- все состояния доступны на `ru` и `en`;
- mobile, keyboard и WCAG AA требования соблюдены;
- реальные данные не используются до production privacy approval.
