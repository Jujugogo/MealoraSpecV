# Mealora — Privacy and Personal Data Spec

**Статус:** draft
**Проект:** Mealora
**Тип документа:** спецификация обработки персональных данных
**Зона ответственности:** персональные данные, demo-ограничения, доступ, хранение, удаление, согласие и production privacy gate
**Дата создания:** 2026-06-19

---

## 1. Назначение документа

Этот документ определяет правила работы Mealora с персональными и чувствительными данными в учебной/demo-версии и фиксирует решения, которые должны быть утверждены до запуска с реальными клиентами.

Документ не является публичной Privacy Policy и не заменяет юридическую проверку. Публичная Privacy Policy должна быть подготовлена отдельно на русском и английском языках перед production-запуском.

Пока документ имеет статус `draft`, он не является финальным источником истины для обработки реальных персональных данных.

---

## 2. Текущий режим продукта

Текущая версия Mealora является учебной/демонстрационной.

Demo-версия:

- не предназначена для приема реальных клиентских заявок;
- не должна использоваться для реальной доставки питания;
- не должна собирать реальные персональные, адресные, платежные или медицинские данные;
- должна использовать только вымышленные тестовые данные;
- не должна списывать реальные деньги;
- не должна использовать реальные платежные реквизиты.

До прохождения production privacy gate использование Mealora с реальными клиентами запрещено.

---

## 3. Потенциально обрабатываемые категории данных

Функциональная модель Mealora предусматривает следующие категории данных.

### 3.1 Данные аккаунта

- идентификатор пользователя;
- данные авторизации, обрабатываемые через Supabase Auth;
- роль пользователя;
- дата создания и обновления профиля.

### 3.2 Контактные данные

- имя клиента;
- номер телефона / WhatsApp;
- иные контактные данные, если они будут добавлены утвержденной спецификацией.

### 3.3 Данные доставки

- город или зона доставки;
- адрес доставки;
- предпочтительная дата старта.

### 3.4 Данные заявки

- выбранный план;
- формат питания;
- количество человек;
- цена пятидневного цикла;
- статус заявки;
- состояние оплаты;
- дата создания и изменения заявки.

### 3.5 Данные о пищевых предпочтениях и ограничениях

- нежелательные продукты;
- обычные пищевые предпочтения;
- легкие непереносимости;
- уровень остроты;
- дополнительные пожелания;
- ответ на high-risk вопрос.

Сведения о непереносимости, аллергиях и медицинских ограничениях могут иметь повышенную чувствительность. В demo-версии разрешены только вымышленные тестовые сведения.

### 3.6 Внутренние административные данные

- внутренние заметки Mealora;
- ручная фиксация согласованной оплаты;
- история административной обработки, если она реализована.

---

## 4. Обязательное предупреждение demo-версии

На форме заявки до ввода контактных данных и пищевых ограничений должно быть показано заметное спокойное предупреждение:

> Это демонстрационная версия. Не вводите реальные имя, номер телефона, адрес, платежные реквизиты или сведения о здоровье и пищевых ограничениях. Используйте только вымышленные тестовые данные.

Предупреждение должно:

- отображаться на русском и английском языках согласно выбранной локали;
- быть доступным с клавиатуры и для assistive technologies;
- не быть скрыто только внутри Privacy Policy;
- появляться до финальной отправки заявки;
- повторяться на demo payment screen в части запрета реальных платежных данных.

---

## 5. Правила тестовых данных

Для demo-версии:

- разработчики, тестировщики и владелец проекта используют только вымышленные данные;
- запрещено копировать реальные клиентские заявки в demo-базу;
- запрещено использовать реальные адреса проживания, личные телефоны и медицинские сведения;
- тестовые данные не должны идентифицировать реального человека;
- скриншоты, презентации, логи и демонстрации не должны раскрывать реальные данные;
- seed data должна быть явно вымышленной;
- demo-аккаунты не должны использовать реальные пароли от других сервисов.

Если реальные данные были введены по ошибке, они должны быть удалены из рабочей базы и доступных логов без необоснованной задержки.

---

## 6. Доступ к данным

### 6.1 Public user

Не может читать заявки, профили, платежные попытки или внутренние заметки.

### 6.2 Customer

Может читать только собственный профиль, собственные заявки и собственные demo payment attempts.

Customer не может:

- читать данные других клиентов;
- читать внутренние admin notes;
- менять role;
- менять административные статусы;
- получать прямой доступ к privileged database keys.

### 6.3 Admin

Может получать доступ к данным заявок только для выполнения административного workflow Mealora.

Admin не должен:

- публиковать данные клиентов;
- копировать данные в неутвержденные внешние сервисы;
- использовать данные вне целей обработки заявок;
- раскрывать внутренние данные публичным пользователям.

Детальные правила доступа и Supabase RLS определяются в `specs/checked-and-approved/TECHNICAL_SPEC.md`.

---

## 7. Безопасность demo-версии

Обязательные правила:

- Supabase Row-Level Security включена для application tables;
- service role keys используются только server-side;
- secrets хранятся в environment variables;
- внутренние admin notes не возвращаются клиентскому интерфейсу;
- сервер повторно проверяет ownership и role;
- клиентская валидация не заменяет server-side validation;
- логи не должны без необходимости содержать полные контактные данные, адреса или сведения об ограничениях;
- debug output с данными заявок не должен попадать в публичный production bundle;
- database backups и exports не должны публиковаться или храниться в общедоступных местах;
- доступ к Supabase dashboard и административным аккаунтам должен быть ограничен владельцем проекта и уполномоченными администраторами.

---

## 8. Хранение и удаление данных demo-версии

Поскольку demo-версия использует только вымышленные данные:

- тестовые заявки могут удаляться после завершения тестирования;
- устаревшие тестовые аккаунты и заявки не должны храниться бессрочно без необходимости;
- перед публичной демонстрацией база должна быть проверена на отсутствие реальных данных;
- перед production-запуском demo-данные должны быть удалены, архивированы отдельно как обезличенные test fixtures или заменены контролируемой seed data;
- случайно введенные реальные данные должны удаляться при обнаружении.

Конкретные production-сроки хранения реальных данных этим разделом не утверждаются.

---

## 9. Privacy notice и согласие в demo-версии

Demo-предупреждение об использовании только вымышленных данных является обязательным.

Полноценное согласие на обработку реальных персональных и чувствительных данных не реализуется как основание для production-обработки, пока не утверждены:

- цели обработки;
- состав собираемых данных;
- сроки хранения;
- правила удаления;
- порядок отзыва согласия;
- список внешних processors;
- правила международной передачи данных;
- публичная Privacy Policy.

Demo-версия не должна создавать впечатление, что тестовый checkbox разрешает Mealora принимать реальные медицинские или персональные данные.

---

## 10. Production privacy gate

До приема первой реальной клиентской заявки должны быть выполнены все пункты:

1. Этот документ проверен, дополнен и явно одобрен владельцем проекта.
2. Документ перемещен в `specs/checked-and-approved/` со статусом `checked-and-approved`.
3. Подготовлена и опубликована Privacy Policy на русском и английском языках.
4. Утверждены точные цели и правовые основания обработки каждой категории данных.
5. Утвержден текст отдельного явного согласия для чувствительных сведений, если такое согласие требуется.
6. Утверждены сроки хранения для аккаунтов, заявок, заказов, платежных записей, admin notes, логов и backups.
7. Утвержден процесс доступа, исправления, удаления, обезличивания и отзыва согласия.
8. Определен контакт Mealora для privacy-запросов.
9. Определены и документированы внешние processors, включая Supabase и будущего платежного провайдера.
10. Проверены регион хранения Supabase и правила международной передачи данных.
11. Проведена необходимая юридическая проверка требований Иордании.
12. При необходимости проведена Data Protection Impact Assessment для чувствительных данных.
13. Реализовано логирование согласия: версия текста, язык, дата и время, user id и связанная заявка.
14. Реализован безопасный процесс удаления или обезличивания данных.
15. Demo warning заменен production privacy notice и корректным consent flow.

Если хотя бы один обязательный пункт production privacy gate не выполнен, Mealora остается demo-системой и не принимает реальные заявки.

---

## 11. Решения, которые остаются открытыми до production

Следующие решения намеренно не утверждены для текущей demo-версии:

- точные сроки хранения каждой категории реальных данных;
- срок удаления данных из backups;
- контактный email или форма для privacy-запросов;
- полный список processors;
- регион production-базы Supabase;
- конкретное правовое основание для каждой цели обработки;
- точный текст production consent;
- процесс проверки личности при запросе доступа или удаления;
- правила хранения финансовых записей;
- необходимость и объем DPIA;
- порядок обработки запроса на удаление при наличии юридической обязанности сохранить отдельные записи.

Эти пункты являются блокирующими для production, но не блокируют разработку demo-версии, если в ней используются только вымышленные данные.

---

## 12. Публичная Privacy Policy

Перед production-запуском должна быть подготовлена отдельная публичная Privacy Policy.

Она должна:

- быть доступна на русском и английском языках;
- использовать понятный клиентский язык;
- описывать категории данных и цели обработки;
- объяснять права клиента;
- описывать сроки хранения или критерии их определения;
- указывать порядок privacy-запросов;
- раскрывать внешних processors и международную передачу данных, если применимо;
- иметь номер или дату версии;
- быть доступной до отправки заявки и из постоянной навигации сайта.

Публичная Privacy Policy не должна храниться только внутри этой внутренней спецификации.

---

## 13. Критерии приемки demo privacy

Demo privacy считается реализованной корректно, если:

- Global Spec явно запрещает прием реальных данных в demo-версии;
- форма заявки показывает двуязычное предупреждение до ввода или отправки чувствительных данных;
- demo payment не принимает реальные платежные реквизиты;
- seed и test data являются вымышленными;
- клиенты видят только собственные тестовые записи;
- admin notes не видны клиентам;
- secrets не попадают в клиентский код;
- RLS и server-side ownership checks включены;
- логи и публичные демонстрации не раскрывают реальные данные;
- случайно введенные реальные данные могут быть удалены;
- production-запуск заблокирован до выполнения раздела 10.

---

## 14. Статус и следующий шаг

Текущий статус документа — `draft`.

Для demo-разработки можно использовать правила разделов 2–8 и 13 как временную безопасную границу.

Документ не может быть рекомендован к production-одобрению, пока не закрыты решения из раздела 11 и не выполнен production privacy gate.
